## Product Overview
`vg-classifieds` is a custom WordPress plugin used in Vineyard Gazette workflows.  
Its primary role is to preserve an existing classifieds publishing process during WordPress/Newspack migration by importing externally prepared classifieds content.

## Current Functionality (Confirmed)
Based on existing internal plugin inventory and notes, the plugin currently:

1. Imports a ZIP file containing HTML classifieds content.
2. Converts that imported content into WordPress entries in a **Classified** custom post type.
3. Supports legacy-to-WordPress workflow continuity for classifieds publishing.

## Current Value
- Reduces manual copy/paste effort for classifieds ingestion.
- Maintains continuity with pre-existing editorial/ad operations.
- Helps migration efforts by mapping legacy classifieds content into native WordPress structures.

## Known Context and Constraints
- Plugin is active in the current site environment (version `0.1.0`, author `Graham Smith`).
- Source code for implementation details is not currently present in this workspace directory, so this baseline captures **confirmed high-level behavior** only.
- Technical specifics (admin UI flow, validation logic, duplicate handling, taxonomy mapping, media handling, error states, permissions) should be documented after code review or runtime walkthrough.

## Users and Workflows (Initial)
- **Primary users:** Admin/editorial or operations staff responsible for classifieds publishing.
- **Core workflow:** Prepare classifieds export -> upload/import ZIP -> content appears as Classified posts -> review/publish in WordPress.

## Technical Functionality Specification (Baseline)
This section captures currently observed behavior and baseline technical expectations.

### 1) Content Model
- **Post type:** `classified` (inferred from behavior; slug/name to confirm in source code).
- **Primary content object:** One WordPress post per classified entry (or grouped unit) generated by importer.
- **Publication model:** Entries are managed through standard WordPress post lifecycle (`draft`, `publish`, etc.), unless plugin enforces custom statuses.

### 2) URL and Routing Behavior
- **Observed single-item pattern:** `/classifieds/<post-slug>/` (confirmed by runtime behavior).
- **Observed archive pattern:** `/classifieds/` likely acts as the post type archive index.
- **Technical implication:** Routing is consistent with WordPress custom post type registration using `rewrite` slug `classifieds` plus `has_archive`.
- **Template resolution:** Archive/single rendering likely follows theme template hierarchy (`archive-{post_type}.php`, `single-{post_type}.php`, or generic archive/single templates) unless plugin overrides rendering.

### 3) Import Pipeline (Confirmed + Inferred)
- **Confirmed:** Plugin imports a ZIP package containing HTML classifieds source files.
- **Expected pipeline:** Upload ZIP -> extract files -> parse HTML -> map parsed records to classified posts -> insert/update posts in database.
- **Open detail to confirm:** Whether importer is create-only or supports update/upsert by unique key.

### 4) Data Mapping Requirements (To Confirm in Implementation)
- HTML source fields should map to:
  - **Post title** (classified headline/category label)
  - **Post content** (body copy from source HTML)
  - **Slug/permalink** (generated or provided)
  - **Optional metadata/taxonomy** (category, location, contact, expiration date, pricing, ad type)
- Character encoding and malformed HTML handling should be deterministic and logged.

### 5) Admin/Operational Behavior (Expected)
- Import is initiated by authorized admin/editor workflow.
- Import operation should provide success/failure feedback and record counts:
  - files read
  - records parsed
  - posts created
  - posts updated
  - records skipped/failed
- Failures should not silently drop records; importer should emit actionable error information.

### 6) Non-Functional Baseline
- **Reliability:** Re-running same ZIP should be safe (idempotent behavior preferred).
- **Performance:** Import should complete within normal WordPress request constraints or use background processing for large ZIPs.
- **Security:** ZIP upload and parsing should validate file type/size and enforce capability checks.
- **Observability:** Basic import logs should be available for troubleshooting.

### Milestone 3 — Include graphics (media from ZIP)

**Goal:** When staff upload the same ZIP the importer already accepts (HTML classifieds plus a sibling **`Graphics/`** directory), images referenced from HTML appear correctly on single classified posts (`vg_classified`) and in the block editor content where applicable.

**Source layout (confirmed from production-style packages):**

- ZIP root contains one or more `.html` / `.htm` files (current importer behavior).
- ZIP also contains a directory named **`Graphics/`** (case may vary; normalize in implementation) holding image files used by those HTML files.
- HTML references images with paths relative to the HTML file, for example:
  - `<img src="Graphics/400_Wceweftz_Tessier4C.jpg">`
- Images are static assets only (no video in scope). Individual files in the example set are well under typical host limits (largest observed ~908 KB); server `upload_max_filesize` / `post_max_size` and WordPress max upload settings still apply per file.

**Expected user workflow (unchanged at the UI level):**

- User uploads one ZIP via **Classifieds → Classifieds Import**, as today.
- The archive may include both HTML and `Graphics/`; the plugin must process both, not only HTML entries.

**Technical approach (plugin-only; no WordPress core changes):**

1. **Discover graphics:** While iterating the ZIP (or in a first pass), collect all entries under `Graphics/` (or `graphics/`) with allowed image extensions (e.g. jpg, jpeg, png, gif, webp). Reject path traversal and non-image types.
2. **Attach to WordPress media:** For each image, copy or stream bytes to a temp file and use WordPress APIs intended for programmatic uploads — e.g. `wp_upload_bits()` or `media_handle_sideload()` after a local temp file — then `wp_insert_attachment()` and `wp_generate_attachment_metadata()` (requires loading `wp-admin/includes/image.php` and related includes in admin context). This is standard plugin practice; **core does not need to be patched** for a plugin to ingest files from an uploaded ZIP.
3. **Map paths to URLs:** Build a map from ZIP-relative paths (e.g. `Graphics/foo.jpg`) to final attachment URLs (or attachment IDs). Handle case and slash normalization.
4. **Rewrite post content:** After creating/updating each classified post body, replace `src` (and `srcset` if present) references that point at `Graphics/...` with the corresponding uploaded media URL. Preserve `alt` and layout where possible.
5. **Idempotency / updates:** On re-import of the same HTML file, if the image bytes change, update or replace the attachment and refresh URLs; if unchanged, skip or reuse existing attachment (align with existing hash logic for HTML).
6. **Reporting:** Extend import results table (or logs) with rows for graphics: skipped, uploaded, failed, linked.

**Image dimensions and resizing (product target: max ~1,000px):**

- **What WordPress does by default:** On attachment, core generates **additional sizes** (thumbnail, medium, large, plus registered sizes) via `wp_generate_attachment_metadata()`. Those are derivative files; the **full-size upload is still stored** unless other logic replaces it. Since WordPress 5.3, very large sources may get a **“big image” scaled** variant (default threshold 2560px on the longest edge), which is not the same as a 1,000px cap.
- **Editorial / performance goal:** Classified graphics should **not exceed ~1,000px** on the longest edge when shown (source ZIPs may contain larger dimensions).
- **Preferred implementation for this milestone:** During import, **resize before attachment** using `wp_get_image_editor()` (or equivalent) so the file written to uploads is already capped (e.g. `max( width, height ) <= 1000`, preserving aspect ratio). Then run normal attachment + metadata generation on that file. That gives predictable file size and front-end dimensions regardless of theme “large” size settings.
- **Alternative (not sufficient alone):** Relying only on core-generated sizes keeps a large original on disk and requires templates or `src` rewriting to point at a named size — easier to miss for arbitrary HTML `img` tags. Prefer resize-on-import if the requirement is a hard cap on displayed/stored pixel dimensions.
- **Idempotency:** Hash or compare dimensions/file size so re-imports do not churn attachments when the effective graphic is unchanged after resize.

**Out of scope for this milestone (unless later expanded):**

- Video or non-image assets.
- CDN-specific URL rewriting beyond what WordPress attachment URLs provide.
- Front-end lazy-loading or image optimization beyond core/thumbnail behavior.

**Compatibility:** Scoped to `vg_classified` and the import pipeline only; no requirement to alter Newspack Plugin or theme templates for basic “images display in post content” behavior.

---

#### FAQ: Can WordPress accept a ZIP that includes media without changing core?

**Yes.** WordPress core already exposes everything a plugin needs:

- The plugin receives the ZIP like any other upload (subject to PHP and server limits on the HTTP request).
- The plugin unpacks it with `ZipArchive` (already required for imports).
- Each image file can be registered in the Media Library using **`wp_insert_attachment`**, **`wp_generate_attachment_metadata`**, and the upload helpers used elsewhere in WordPress (e.g. sideload or `wp_upload_bits`). No core file edits are required.
- Practical limits are environmental: max request size for the ZIP, per-file size, execution time, and disk space — not a fundamental “WordPress can’t do ZIP + images” restriction.
